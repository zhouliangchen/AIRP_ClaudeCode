启动游戏的文件夹即为本次游玩的存档文件夹。

目前游戏支持四种启动方式，导致存档文件夹的内容会出现部分差异：
1.标准角色卡：png格式的角色卡文件，JSON 数据嵌入在图片的 `tEXt` 块中（keyword 为 `chara`），base64 编码。系统会使用 `import_prepare.py` 解析，得到无内嵌的纯PNG图片（可用于后续图片生成参考），和得到的json角色卡数据（name、description、personality、first_mes、scenario、世界书等）
2.文本资料包启动：txt/json/md格式的文本资料包，系统会使用 `import_prepare.py` 解析，尝试对文本资料进行分析，并生成存档文件。
3.旧存档：检测到 `chat_log.json` 与 `memory/` 后，系统会继续使用旧存档，继续游戏。开发阶段的本项目不保证对旧版本存档的兼容支持。
4.空白启动：当前文件夹没有png/txt/md/json/旧存档时，系统会以空白模式启动；若当前文件夹还存在其他文件，claude code会询问用户是否清空当前文件夹后再启动。空白启动状态下，系统不会自动生成开场，而是由玩家负责开头。系统会在游玩过程中基于玩家引导和剧情驱动逐渐形成并更新迭代存档文件。

chat_log.json   交付给前端的聊天记录权威源，包含用户每一轮的角色通道输入、系统正文输出（包含player/character agent的对话）。每轮成功交付后追加到文件末尾，供前端渲染使用。前端显示时，用户亲自输入的角色通道消息用 `characters/player.md` 中的当前角色名加 `(user)` 标记，例如 `雨蒙(user)`；由 player agent 代演同一角色生成的台词只显示角色名，例如 `雨蒙`。

content.js 前端渲染聊天内容的镜像文件，基于chat_log.json生成；每个已交付 turn 会带有 `data-round-id="round-000001"` 这类稳定轮次标识，编号与 `chat_log.json` 中的可见交付轮次顺序一致，用于把 `.card_assets.json` 中 `display_policy: "story_inline"` 且 `round_id` 匹配的剧情插图挂回对应轮次文本中/文本后，而不是集中显示在最新轮次。`content.js` 还负责把用户输入框标题渲染为 `<角色名>(user)`，把 `character_dialogues` 渲染为独立对话框，并根据 `after_paragraph` 保持对话框与正文段落的相对位置。图片 worker 完成并写入 `.card_assets.json` 后，必须重建浏览器实际加载的 `skills/styles/content.js`，否则前端刷新也只能读取旧的 `CARD_ASSETS` 快照。

.agent_runs/  agent运行的临时文件区；普通轮次目录命名为 `.agent_runs/round-000001`，存档回滚重演轮次目录命名为 `.agent_runs/round-000001-replay-001`。其中第一个数字仍对应玩家输入次数/原始轮次，被回滚次数不计入；`replay-001` 对应该存档第1次触发回滚重演，同一次回滚覆盖的多个受影响输入共享同一个 replay 序号。普通轮次若因 delivery、critic 或外部调用失败而未交付，重新准备同一玩家输入时必须复用对应的 `.agent_runs/round-xxxx`，清理该目录内旧的阶段输出、intents、artifacts 和 memory job，不得因为失败尝试递增到下一玩家输入轮次。每轮交付后，`post_round_memory_jobs/` 与 `post_round_objective_memory_jobs/` 会分别记录角色个人记忆整理和 GM objective 资料整理任务，这两类任务可以并行执行；任一任务状态仍为 `pending` 或 `degraded_memory_state` 时，下一轮用户输入必须被服务端阻塞，直到记忆整理完成或被显式修复。
.agent_runs/<round>/story.output.json 中，玩家或重要角色的直接台词、自由行动、私密想法或长期选择，默认必须能从 `story_input.loop_outputs.actors` 或 side-thread `actor_outputs` 追溯到对应 actor 输出；但闪回、记忆、梦境、象征性场景、retcon回顾等特殊场景内部，GM/subGM临时代演的重要角色行为可以作为该特殊场景内的 story 来源。特殊场景结束后的现实场景仍恢复 actor 输出来源要求。

generated/  由assets-ui agent生成的资源文件夹，包含图片、UI脚本等资源；其中 `generated/jobs/` 保存 assets-ui runtime planner / worker 的任务状态文件，记录 queued、deferred、failed、completed、waiting_on_style_reference、waiting_on_references、waiting_on_critic 等状态，以及显式 defer 或失败原因（如 `asset_worker_not_configured`、`image_generation_failed`、`reference_image_not_supported`）。

generated/jobs/<job-id>.json  图片作业状态文件；scene job 的 `prompt` 应是 assets-ui 优化后的镜头化绘图提示词，包含画面目标、镜头设计、构图主体、动作情绪、光线氛围、参考图用途和负面约束，而不是 story 正文流水账。若 `reference_candidates` 同时包含多张图片，prompt 必须逐条写明每张参考图的相对路径、文件名和引用目的，例如具体角色人设参考、画风参考、场景氛围参考或其他设定参考。持续剧情插图需求下，scene job 即使来自 assets-ui planner，也必须保留或补齐 `characters`、`character_appearances`、`reference_policy` 和 `reference_candidates`；参考图应至少包含本轮出场重要角色的当前人设图，并在已有历史剧情插图时追加最近一张完成的 `generated/images/*.png` 作为画风、镜头氛围和场景质感参考。剧情插图 scene job 必须记录 `round_id`；若 assets-ui planner 未提供，运行时会补为当前 `.agent_runs/<round>` 名称，供前端按轮次显示。图片 worker 完成后，job 文件还会记录 `frontend` 刷新结果；若 `.card_assets.json` 已更新但 `skills/styles/content.js` 重建失败，则保留 `status: "completed"` 并写入 `frontend_sync_error`。当主图片 API 失败但备用图片 API 成功时，job 文件必须记录 `provider_fallback`，包含脱敏后的失败原因、来源 provider 和目标 provider。无画风参考图时首个人设图任务会扩展为三张 `character_reference_candidate` 候选；候选完成后会产生 `character_reference_selection` 作业，critic agent 返回 `winner_candidate_id` 后，胜出图移动到正式 `generated/characters/...` 路径，淘汰图移动到 `generated/tmp/<batch>/rejected/`，critic 不可用或返回无效时状态保持 `waiting_on_critic`。
assets-ui planner 输出的 scene job 若明显是剧情插图任务但遗漏 `queue_type`，运行时会在严格校验前补齐为 `scene_illustration`，并补齐默认的 `display_policy: "story_inline"`、`camera_perspective: "third_person_camera"` 和 `scene_mode: "story_scene"`；非字符串或不受支持的 `queue_type` 仍必须拒绝。assets task 的调度状态以实际落盘结果为准，图片 worker 可以异步运行，但 pump 不得把已经 deferred、waiting 或 failed 的任务伪报为 started。

若存档没有任何可用参考图片，assets-ui 生成剧情插图时应在图片 prompt 中要求根据剧情题材、时代、情绪、场景和角色状态智能匹配画风；用户通过指令通道明确调整画风时，应记录为 `art_style` 并优先使用；

generated/characters/<角色名>/<角色名>-<外观状态>.png  同一角色的外观状态人设图；场景插图必须优先匹配当前剧情外观状态，缺少匹配人设图时应先创建该状态的人设图，再生成场景图；共享记忆形态仍存放在 canonical 角色目录下，长期独立记忆形态若被注册为新的重要角色，则使用其独立 canonical 角色目录；已有高质量画风参考或存档画风已稳定时，多个人设图任务可以并行启动；没有参考图且画风尚未稳定时，应避免多角色人设图同时无参考生成，以免同一存档内风格不统一；

</memory文件夹>

<characters文件夹>(根目录/characters，不是memory/characters)
characters/<角色名>/profile.md  角色的基本设定，与memory/characters/<角色名>/profile.md同步更新，内容保持一致；区别在于此文件为角色的第一人称口吻自我介绍。此文件由GM agent维护，供player/character agent读取；player/character agent不能修改此文件；

characters/<角色名>/long_term_memories.md 角色的长期记忆，由player/character agent自行维护；记录着角色的背景、经历、关系、目标等，作为角色的常驻上下文；上限为1000字，player/character agent在回合结束整理记忆时需要注意控制字数；否则会触发hook，提示长期记忆字数过多，要求角色重新整理；

characters/<角色名>/key_memories.json 角色的重点记忆，由player/character agent自行维护；以关键词标签索引的形式记录着角色对某件事的详细记忆，作为角色的可召回上下文；结构为记忆标签（上限20字）、记忆摘要（上限100字）、记忆详情（上限600字）；其中记忆标签、记忆摘要会常驻在上下文中，未召回时以“可进一步回忆"<标签>"：<摘要>”展示，避免与真正的“我想回忆：<标签>”召回触发词混淆；记忆详情仅在角色主动回忆时才会被注入上下文，召回后同一段记忆改为“我已经回忆起"<标签>"："<摘要>"，详情为"<详情>"”展示；若在回合内互动阶段召回，detail 通过 `.agent_runs/<round>/artifacts/actor.recalled_key_memories.json` 保持到本轮 post-round 个人记忆整理结束，同一 actor 在本轮后续再次被调度时也必须看到已召回状态；若是在整理记忆阶段进行召回，则追加到同一 sidecar 并在该整理任务重跑时可见；本轮 post-round 个人记忆整理全部成功写回后，控制面会重置这些已召回状态，pending 或 degraded 时不得清理；角色最多可同时拥有16条重点记忆；

characters/<角色名>/short_term_memories.md 角色的短期记忆，由python控制面自动维护；仅当角色收到经过projection审核/编辑后实际投递的GM/subGM自然语言消息并完成回复后，才将这一组输入输出一起写入短期记忆，避免未完成的GM/subGM单向消息或未投递的原始actor_calls prompt提前沉淀；格式使用“记忆的回声：<GM/subGM消息>”和“我：<角色回复>”，每条消息后空行分段；短期记忆无字数限制，但每轮剧情结束后，在记忆整理完成后，系统会自动清空短期记忆。特殊场景结束后，只有GM/subGM明确选择性告知目标角色、并实际投递给该actor的第二人称自然语言内容，才能进入该角色短期记忆；梦醒遗忘、他人梦中行为、仅供GM伏笔的内容不得直接写入本人短期记忆。

characters/player.md 存储玩家目前操作的角色名和相对文件路径，用于映射到对应的characters/<角色名>/文件夹；格式为两行纯文本：`name: <角色名>` 与 `path: characters/<角色名>`。角色名称尚不明确时，允许以player、actor1、actor2等名称占位，并创建对应的角色存档目录；在名称明确后，input-analyst agent可根据用户指令触发角色更名。`characters/_self/` 已弃用，运行时不得再创建或读取；

</characters文件夹>
